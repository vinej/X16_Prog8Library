# desktop — a launcher for the Commander X16

Icons are VERA sprites over a photographic wallpaper. Drag one with the mouse to
move it; double click it, or press its number, to run the program it stands for.
When that program finishes, **the desktop comes back, with the icons where you
left them**.

```powershell
.\build.ps1 -Run          # the desktop
.\build.ps1 -Proof -Run   # just the launch/return round trip, no UI
```

| File | What |
|---|---|
| `build.ps1` | builds the desktop and everything it can launch |
| `desktop.p8` | the launcher: sprites, mouse, and the launch path |
| `relaunch.p8` | the round trip on its own — the part worth reading first |
| `child.p8` | a program to launch, which prints and returns |
| `sub/subchild.p8` | a program in its own directory, with a data file beside it |
| `build/DESKTOP.CFG` | the list of programs, written by the desktop itself |
| `build/WALL.BMX` | the 640x480 wallpaper, generated by `build.ps1` if absent |

It also launches `kalk`, `hello` and `imgview`, which live in their own example
folders; `build.ps1` builds those too, since the desktop loads them by name.

## The wallpaper

The background is a 640x480 8bpp image on the **VERA_2 layer** — 307,200 bytes,
which is why it lives in that board's own SDRAM and not in VRAM, where it would
not fit at any resolution above 2bpp.

The part that makes it a desktop rather than a picture is `CTRL bit3`,
**passthru**. With it set, VERA's opaque pixels draw over the bitmap and the
bitmap fills in wherever VERA is transparent (see `vera_2.md` §2 and §8). Since
background colour 0 is transparent, a text cell painted with it is a window onto
the photograph: the text layer stops being a backdrop and becomes a sheet of
glass with writing on it. The sprites ride over the top on the same rule, for
free — which is the whole reason dragging an icon still costs one `sprite_pos`
write and not a redraw.

The VERA_2 palette is its own, so a 256-colour photograph cannot disturb the 16
colours the text layer draws with.

Two things about transparency, one of which cost a title bar:

* **Background colour 0 is transparent**, which is what the whole arrangement
  rests on.
* **Foreground colour 0 is transparent too.** The title bar was black on light
  grey, and the black lettering came out cut *through* the bar, showing sky
  through the strokes. It is blue on light grey now. Captions get a dark grey
  plate for the same reason in reverse: white on an arbitrary photograph is a
  coin toss.

**A launched program gets a plain machine.** The desktop switches the layer off
before handing over, and that is not tidiness: under passthru, background colour
0 is transparent, and colour 0 is what an ordinary program draws on. Launching
`kalk` with the layer still up put the photograph behind its row headers, which
read as a corrupted font rather than as what it was. The mirror of the `imgview`
bug earlier in this file — there, a program failed to clean up after itself;
here, the desktop failed to clean up before letting go.

Without the VERA_2 layer there is nothing to show through to, so `gfx8h_has`
decides: no layer, and the desktop paints its old blue backdrop and behaves
exactly as it always did. Everything else — geometry, captions, dragging — is
identical either way.

## Appearing all at once

The desktop is rebuilt from nothing every time it comes back: display mode,
charset, sprite pixels, 307 KB of photograph, then every character of text. Done
on a live screen that is exactly what it looks like — a clear, a backdrop, a
title bar, captions arriving one after another, the photograph wiping down over
whatever the last program left in SDRAM.

So it is all done in the dark. The text layer is switched off in `DC_VIDEO`
before anything is drawn, `bmx_load_hires` never touches `CTRL` so the image can
stream into SDRAM with the layer disabled, and `reveal()` turns the text layer
and the bitmap on together. The desktop appears in one frame or it does not
appear at all.

Measured with the border colour as a stopwatch — it stays visible while the text
layer is blanked — the whole rebuild takes **about 30 ms**, image load included.

One flash that *can* be avoided is the display mode. Setting it blanks and clears
the screen on the way through, and a program that tidied up after itself has
already left mode 0 behind, so both the desktop and `kalk` ask `screen_get_mode`
before setting it.

What is left belongs to the launch itself, and the desktop cannot suppress it:
two PRG loads, and each program initialising the machine for itself. Those
flashes happen inside the other program.

## Putting programs on it

`p` opens a picker: a directory browser over the wallpaper, directories
first, then anything ending in `.prg`, then everything else marked
`[dat]`. Enter descends into a directory, `..` climbs back out. It wears
the title bar's colours — blue on the same light grey plate, the
selected row inverted — so the two read as parts of one desktop rather
than two programs.

## Opening a file with a program

A `.bmx` or a `.csv` is not something the desktop can run, but it is
something a program on the desktop can open. Enter on a `[dat]` row asks
**which** — a short list of the icons you already have — and then that
program is what gets launched, with the file handed to it.

The handoff is `x16lib/launcharg.p8`: the path goes in golden RAM at
`$0500` behind a magic, and the program reads it with `launcharg.get()`
on the way in. It is the X16's missing `argv`, in about forty lines.

The browser itself now lives in `x16lib/filepick.p8`, shared: this
desktop opens it with `filter("*.*")` and `primary("*.prg")`, imgview
opens the same one with `filter("*.bmx")`. What stays here is what only
a desktop wants — keeping an entry, choosing its icon, and handing a
data file to a program that can open it.

A program that only needs a file *at startup* still needs no browser at
all: `launcharg` is cheaper and means one browser, one set of keys, one
look. kalk works that way of necessity as well as taste — it is within
3 KB of the low-RAM ceiling and the module costs 4 KB.

Two things a launcher must get right, both learned the hard way:

* **Clear it when passing nothing.** Golden RAM keeps what the last
  program left there, so without a clear the second launch of a program
  inherits the file the first one was given. `launch_path` clears before
  every launch and sets only when there is something to set.
* **Do not trust the header line's type.** The picker skips
  `DIR_TYPE_NONE` entries because a real card reports its volume label
  that way, while an emulator's host filesystem reports a path as
  `DIR_TYPE_HOST`. Listing programs only, that difference never showed;
  listing everything, it put a row of raw directory bytes on screen.

On a program it offers two things, and the cheap one matters most:

* **`r` runs it now** — no icon, no label, nothing written down. Most of
  the time that is all you wanted.
* **`a` keeps it** — name it (the program's own name is filled in, and is
  usually right; `MYGAME.PRG` is not a caption, so it is editable), pick
  an icon from the presets, and it joins the desktop.

The list lives in `DESKTOP.CFG` at the root of the card: sixteen
fixed-size records holding a path, a label, an icon and a position. Fixed
sizes because reading and writing them is then two loops rather than a
parser, which is what you want on a 6502; the cost is a stated ceiling —
41 characters of path, 15 of label — rather than a surprise later. It is
saved when you add a program and when you drop an icon, so an arrangement
survives the power being cut, not just a launch.

The desktop reads that list on every entry, which is why it also holds
the positions: there is nowhere else they need to live.

**Where a program runs.** A program with data files beside it opens them
by bare name, so it has to run from its own directory. The launcher
splits the stored path, `dos_chdir`s into the folder, and hands the
trampoline only the filename. `sub/subchild.p8` exists to prove exactly
that: it reads `SUBDATA.SEQ` by bare name and says so.

Coming back needs no matching climb, which was the pleasant surprise. A
path works in a filename anywhere the KERNAL takes one, so the trampoline
reloads the desktop as `/desktop.prg` from wherever the program left the
drive, and the desktop's first act is `dos_chdir("//")`. The 54-byte stub
never learns what a directory is.

**Two encodings meet here**, and both bit me. The drive returns filenames
in **ASCII** — `b` is `$62` — while Prog8 encodes a lower-case letter in
source as PETSCII `$41-$5A`, which are the codes of ASCII *capitals*. So
matching `.prg` means folding the drive's byte with `& $DF`, and a
filename used as a default caption has to be folded the same way or it
SHOUTS next to the hand-written ones. The `| $20` an ASCII habit reaches
for corrupts a perfectly good lower-case name.

**The type field is no filter.** The X16's host filesystem reports every
file as `PRG` — source, images, all of it — so the picker matches on the
name instead. A program not ending in `.prg` will not be offered, which
is the price of not listing the whole card.

## Coming back is the hard part

A PRG loads at `$0801` and overwrites whatever was there, so a launcher cannot
call a program and expect to still exist afterwards. It cannot even *load* one:
the moment `LOAD` runs, the caller's own next instruction has been replaced by
the incoming program. My first attempt did exactly that and fell into the
machine-language monitor.

What survives is **golden RAM, `$0400-$07FF`** — the KERNAL does not use it,
BASIC does not use it, and Prog8 only uses it if asked. A fifty-four byte
trampoline goes there and does the whole job from outside `$0801`:

```
SETNAM / SETLFS / LOAD   the program
JSR  <program entry>         ; it owns $0801.. now
   ...it returns...
SETNAM / SETLFS / LOAD   the desktop, back off disk
JMP  (<desktop entry>)
```

The trampoline refers only to fixed golden-RAM addresses and the KERNAL jump
table, never to itself, so it can be copied to `$0400` and run there. Icon
positions live in golden RAM too, just above it, so they survive the round trip
without touching the disk.

Entry addresses are **read, not assumed**. Prog8 emits `SYS 2071` today, but that
number moves with the stub text, so the SYS argument is parsed out of each PRG's
BASIC stub — read *off disk*, since loading a program to find out where it
starts would defeat the point.

Both programs here did that by hand at first, in forty lines each. It is now
`cx.fs_prg_entry(name, len, 8)`: writing the same fiddly parser twice was the
argument for putting it in the library, and getting it wrong once (the entry is
`$0817`, not the `$080D` I assumed) was the argument for it being worth testing
there rather than here.

## What makes a program launchable

**It has to return.** Prog8's `start()` falling off the end is an `RTS` straight
back into the trampoline. Two things break it:

* a program that ends in an endless loop (`repeat { }`) never comes back — that
  rules out `shapes` and `sortdemo` as they stand
* a program that uses golden RAM for itself overwrites the trampoline

`kalk` is launchable: Run/Stop leaves its loop, it restores the screen, and
`start()` returns. `imgview` was not — it ended in `repeat { }` — so it now
waits for `ESC` (or Run/Stop) and returns. Other keys are ignored, so a stray
press cannot dismiss a picture you are still looking at.

**Restoring the screen means more than `screen_reset`.** `imgview` draws on the
VERA_2 bitmap, and `screen_reset` is `CINT`, which only restores the primary
VERA. The first time the desktop launched it, the round trip worked perfectly
and the screen still showed the photo: the desktop was underneath, hidden by a
bitmap layer nobody had switched off. `imgview` now calls `gfx8h_off` before it
returns — and the desktop calls it on the way *in* as well, because trusting
every program to clean up after itself is how you get an invisible desktop.

## Using it

Drag an icon to move it. The label is rubbed out when you pick the icon up and
redrawn when you put it down, so only the sprite follows the mouse — text can
only be moved a whole character cell at a time, and a caption stuttering
between cells while the icon glides by the pixel looks broken.

It lands on the first text row *entirely* below the icon; rounding down instead
would tuck the label under the icon's own sprite as soon as a drag left the
8-pixel grid. A drop redraws every caption, not just the moved one, because
blanking the dragged label on pick-up can clip a neighbour's if the two
overlapped.

Double click within half a second to launch. `p` -- or the `[programs]` button
at the right of the title bar -- opens the picker. `Run/Stop` quits.

A return repaints from scratch -- the launched program owned the whole machine,
so nothing on screen is assumed to have survived it. The wallpaper is the one
exception, and it is worth the exception: 307 KB off the card is about two and
a half seconds, and paying it on every return was the black screen between a
program quitting and the desktop coming back.

VERA_2's SDRAM is not VERA's VRAM. The only door into it is `$9F65`, so a
program that never touches those registers cannot have disturbed the picture.
The desktop fingerprints what is in the framebuffer -- the leftmost column,
one byte per row, summed -- and stores it in golden RAM. On the way back it
takes the fingerprint again: match means the photograph is still there and
there is nothing to fetch. A program that did use the layer changes those
bytes, and a reset clears SDRAM outright, so both fall back to loading. The
failure mode is a needless load, never a wrong picture.

Measured: 143 frames to load, 2 frames to recognise it was already there.

The pointer needs `mse_config(1, 80, 60)` rather than `mouse_show`: with a size
of zero `MOUSE_CONFIG` keeps whatever bounds are already set, and on a fresh
boot there are none, so the pointer never appears.
